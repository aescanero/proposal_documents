01

Why this talk

Three questions every platform team is asked, usually during an incident.

~4 minutes for this section.

Three questions you should answer in one minute

What is running?

Not what the chart says. The actual objects, fields and versions, per environment.

Why is it like this?

Which change, which review, which person approved this exact field value.

What will this PR do?

Before merge. Not "bumps chart 4.2 → 4.3", but the objects that will change.

If any answer needs "let me re-render it with the version we had back then", the translation lives outside your history.

Ask the room: who can answer question 3 for a Helm chart bump today? Usually few hands.

Everything in this talk is about making those three answers a git command.

Most teams version their intent.
Few version the translation of that intent.
The incident is always in the translation.

Translation = templating, defaults, overlays, generated code, values merged from three files. That is where the surprises are: a default changed upstream, a template conditional flipped, a CRD grew a field.

02

From scripts to declarative

A short history, so we agree on the words.

~5 minutes. Skip quickly with an expert audience.

Four generations of change management

Scripts

Imperative. Run these commands in this order. The state is whatever happened. Re-running is dangerous.

Config mgmt

Convergent. Describe resources; an agent nudges each host towards them. Idempotent, but per host.

IaC

Declarative + plan. Desired state in files, a state store, a diff (plan) before change. Usually pushed from CI.

GitOps

Declarative + continuous reconciliation. Git is the desired state; an agent in the target pulls and corrects drift.

Each step moved more of "what should exist" into reviewable files. The next step moves "what it expands to" there too.

Note the shift: from "steps" to "state", from "once" to "continuously". The plan in IaC was the first time reviewers saw the effect — but it is ephemeral.

The reconciliation loop

The loop is the same in Kubernetes controllers, config management agents and GitOps operators. The interesting question is: what exactly is "desired state" — the template, or the rendered output?

Push vs pull delivery

Push

  • CI runs the change on merge (apply, helm upgrade).
  • Credentials to the target live in CI.
  • Runs once per change; drift is found by a separate job.
  • Natural fit for cloud APIs and stateful resources.

Pull

  • An agent inside the target watches git.
  • No inbound credentials from CI to the cluster.
  • Runs continuously; drift is corrected automatically.
  • Natural fit for Kubernetes objects.
Keep this axis separate in your head: push/pull is about who reconciles. Hydration is about what is stored. They are independent.

This is the single most important clarification of the talk. People conflate "GitOps" with "pull", and "SHIM" with "push". SHIM works with either.

03

GitOps: principles and practice

What it gets right, and where it quietly leaves a gap.

~8 minutes.

The four OpenGitOps principles

1 · Declarative

The system's desired state is expressed declaratively.

2 · Versioned and immutable

Desired state is stored so it enforces immutability and versioning, with a complete history.

3 · Pulled automatically

Software agents pull the desired state declarations from the source.

4 · Continuously reconciled

Agents observe actual state and attempt to apply the desired state.

These come from the OpenGitOps working group (a CNCF project). Paraphrased, not verbatim.

Notice what principle 2 says: the desired state is versioned. It does not say which form of it.

A typical GitOps setup

The controller fetches, renders Helm or Kustomize with its own embedded engine version, diffs against the cluster and applies. The rendered output exists only in the controller's memory and, eventually, in the cluster.

What GitOps gets right

  • One source of truth for intent, reviewed via PR.
  • Drift correction without humans.
  • No CI → cluster credentials in the pull model.
  • Rollback = revert a commit.
  • Audit of who changed the intent, and when.

Where it shines

Stateless workloads on Kubernetes, many clusters, fleets that must converge to the same baseline, teams that want "merge = deployed" with no pipeline glue.

Be fair here — GitOps solved real problems: snowflake clusters, kubectl-from-laptops, unknown state. Nothing in this talk argues against those wins.

Where the gap opens

Reviewed diff ≠ effect

The PR shows version: 4.2.0 → 4.3.0. The effect is hundreds of changed lines nobody saw.

Engine version decides

The controller's embedded Helm/Kustomize version shapes the output. Upgrade the controller, change every app.

Not reproducible later

"What did we deploy on the 3rd?" needs the same chart, values, engine and cluster capabilities as on the 3rd.

Policy sees it last

Admission control is the first thing that evaluates the real objects — at deploy time, not at review time.

None of these are bugs in a specific tool. They follow from "render at sync time".

Two more limits, outside Kubernetes

Cloud infrastructure

To reconcile VPCs, databases and IAM by pull, you need an operator per cloud API, running with powerful credentials inside a cluster that the same infrastructure hosts.

Stateful resources

Continuous correction is perfect for a Deployment. For a database, a key or a network, "correct the drift" can mean destroy and recreate. Some drift must be decided by a human.

Continuous self-healing is a feature for cattle and a risk for pets.

This is why many organisations run GitOps for apps and a push pipeline for infrastructure, and then struggle to explain one model to auditors.

Secrets: every model's sore spot

  • Git must never hold a secret value — encrypted or not, the history is forever and every clone carries it.
  • GitOps answers: sealed/encrypted secrets in git, or references resolved in-cluster (external secret operators).
  • References win: git holds which secret, the runtime identity reads what.
Keep this in mind: the moment you store rendered output in git, a chart that renders a Secret with data becomes a leak. Hydration needs a guard here.

This becomes a hard rule in the SHIM section: a rendered Secret carrying a value fails the render.

04

The hydration gap

Intent → translation → output. Where does the middle step live?

~5 minutes.

Three layers of any configuration

Vocabulary: "dry" configuration is the intent plus templates; "wet" or "hydrated" configuration is the output. "Hydrating" = running the translation and keeping the result.

Worked example: a one-line chart bump

What the reviewer sees

# values/prod.yaml
 chart: ingress-controller
-version: 4.2.0
+version: 4.3.0

1 line. Approved in 30 seconds.

What actually changes in the cluster

# Deployment/ingress-controller
-        image: …/controller:v1.9.6@sha256:…
+        image: …/controller:v1.10.1@sha256:…
+        - --enable-annotation-validation=true
# ClusterRole/ingress-controller
+  - apiGroups: ["discovery.k8s.io"]
+    resources: ["endpointslices"]
# ValidatingWebhookConfiguration
-    failurePolicy: Ignore
+    failurePolicy: Fail
# … 280 more lines across 14 objects
A changed RBAC rule and a webhook that now fails closed — reviewed by nobody.

Illustrative example, not a specific chart release. The pattern is real: minor chart bumps routinely change RBAC, webhooks, defaults and probes.

The question is not "was the bump wrong" but "did a human decide on these 280 lines".

Where can the translation run?

WhereWho sees the outputWhen
In the controller, at syncThe controller, then the clusterAfter merge
In CI, discardedA log, if anyone reads itBefore merge, not kept
In CI, committed to a separate "wet" repoReviewers of a second PRAfter the first merge
In CI, committed in the same PRThe reviewer of the changeBefore merge, kept forever
Only the last row answers all three questions from slide 4 with git log and git diff.

The separate wet repo is a legitimate design (it keeps the dry repo small), but it splits review in two and needs its own sync automation. We'll come back to this trade-off.

05

Source-Hydrated Infrastructure Models

SHIM: keep the fully translated state in git, before reconciling.

~10 minutes. The core of the talk.

Definition

A source-hydrated infrastructure model keeps in version control, reviewed and immutable, the fully translated state that sits between the abstract intent and what is deployed — and produces it before reconciliation, not during it.

Hydrated

Every field resolved: no template left to evaluate at deploy time.

In the source

Committed next to the intent, in the same change, under the same review.

Model

The whole system's declared state, not one app's manifest.

"Model" matters: it is not only Kubernetes YAML. It can include generated IaC, resolved dependency graphs, address allocations — anything derived from intent.

The pipeline, end to end

Translation and reconciliation are separated by a merge. The thing that gets reconciled is exactly the thing that was reviewed.

Principle 1 · Translation is separated from reconciliation

  • The translator runs in CI with pinned versions (template engine, target API version).
  • The reconciler never translates: it applies objects, or diffs objects.
  • Upgrading the reconciler no longer changes what gets deployed.

Consequence

You can switch reconcilers — a pull agent, a CI job, an IaC tool — without changing a single committed object. The model is the contract; the reconciler is replaceable.

This is the property that makes SHIM delivery-agnostic.

Principle 2 · An integrity gate proves hydrated = source

# in every PR, without cloud credentials
./render-all.sh                      # translate with pinned tools
git status --porcelain -- '*/rendered/*'   # must be empty
  • A hand edit in the hydrated output → fails.
  • A template or version bump without re-rendering → fails.
  • The gate must prove it ran: rendering zero files is a failure, not a pass.
A gate that cannot run is worse than no gate: it reports success.

The last bullet is learned the hard way: a glob that matches nothing, a policy namespace that evaluates nothing — all exit 0. Every gate should count what it checked and fail on zero.

Principle 3 · Policy runs on the output, in the PR

Admission policies (Gatekeeper/OPA, Kyverno…) can evaluate the hydrated objects offline:

gator test --filename=policies/ \
           --filename=stack/rendered/
conftest test rendered/ --policy policy/

Effect

"This pod tolerates a node pool it does not own", "this image has no digest", "this service account carries another environment's prefix" — fail the PR, not the deploy.

Admission stays as the last line of defence; the PR becomes the first.

Without hydration, offline policy checks need someone to render on the fly — which is the same in-flight rendering we are trying to remove.

Principle 4 · Promotion is a diff

With every environment's model hydrated, promoting from qa to prod is visible as:

diff -r envs/qa/rendered envs/prod/rendered

The only differences should be the ones you intend: size, region, hostnames.

What it catches

  • An environment that silently diverged.
  • A default that equals one environment's real value.
  • A copy-pasted environment carrying the old name.

Same idea as "promote the image digest, never rebuild": what was tested is byte-identical to what is promoted, except for the declared differences.

Principle 5 · Late-bound values are named, never faked

Some values only exist at apply time: an IP allocated by another stack, a generated ID.

spec:
  loadBalancerIP: late:edge.ip_address
  replicas: 3

The reviewer sees exactly which fields are not known yet.

Never a mock

A realistic-looking fake (10.0.0.5) passes review as if it were real. A named marker cannot be mistaken for a value.

The marker is masked when comparing rendered vs applied after deploy. Everything else must match exactly.

Principle 6 · Some things are never hydrated

WhatWhyInstead
Secret valuesGit history is forever; every clone is a copyRender fails on a Secret with data; secrets come from a runtime store by reference
Bulky CRDsOften >90 % of a render; unreadable diffsA digest per CRD — a change shows as a changed hash
Cluster lookupsTemplates that read the live cluster render differently offlineForbidden in your own templates; tracked per third-party chart
The planDepends on current state; stale in minutesReviewed in the PR, not versioned

Part 2 shows measured numbers for the CRD point on a real chart: about 97 % of the rendered bytes were CRDs.

Principle 7 · Prove that applied = reviewed

  • After each apply, fetch what the target actually holds (e.g. the release manifest) and compare it with the committed output.
  • Mask only the named late-bound fields.
  • A difference fails the step and is recorded as drift.

Catches

  • A deploy tool embedding a different engine version than CI.
  • Templates that consult the cluster.
  • A target API version out of step with the pinned one.
Without this check, the hydrated output is a claim nobody verifies.

This closes the loop: review the output, gate the output, apply, and prove the output is what landed.

GitOps vs SHIM, side by side

Not competitors: SHIM changes what is stored; GitOps describes how it is reconciled.

~7 minutes.

Comparison

Classic GitOpsSource-hydrated
Git holdsIntent: charts, overlays, valuesIntent and its translation, raw
Translation runsIn the controller, at syncIn CI, before merge; result committed
Reviewer seesThe change of intentThe change of intent and its exact effect
"Why did X happen?"Re-render with the engine of the timegit log -p on the object
PolicyAt admissionOn the output in the PR, and at admission
ReconciliationPull agent, continuous, self-healingIndependent: push or pull
Engine upgradeChanges every app at onceA normal PR with a visible diff

Walk the table row by row; it is the summary slide people photograph.

Trade-offs, honestly

SHIM gives you

  • Review of the effect, not the intention
  • Nothing rendered in flight
  • Full audit trail per field
  • Policy before deployment
  • Promotion as a diff
  • Reconciler independence

SHIM costs you

  • Large diffs and noisy PRs
  • Merge conflicts in generated files
  • An integrity gate you must maintain
  • A secret-leak risk to guard
  • More CI time
  • Values known only at apply stay unknown

Mitigations for the costs: CRDs as digests, stable ordering of objects, regenerate on conflict instead of hand-merging, CODEOWNERS on generated paths so reviewers know where to look.

Push or pull under SHIM?

SHIM + pull

A GitOps agent syncs the hydrated path, with its own rendering disabled. Keeps self-healing; the agent never translates.

Good for: fleets of stateless clusters.

SHIM + push

CI applies the hydrated model on merge with a per-environment identity; drift is detected on a schedule and decided in a PR.

Good for: cloud infrastructure, stateful resources, strict identity boundaries.

Choose the reconciler per resource class. The hydrated model is the same either way.

Part 2 explains why one platform chose push for everything, including Kubernetes, and what it gave up.

Tooling families (neutral examples)

FamilyExamplesRole in a SHIM
Configuration as datakpt (dry/wet packages), Kustomize, Jsonnet, CUETranslators whose output is committed
Template engineshelm template, Timoni, cdk8sRender in CI with a pinned version
IaC generatorsTerramate, CDK for Terraform, Pulumi programsGenerate committed IaC from higher-level intent

Offline policygator, conftest, kubeconform, Kyverno CLIGate the hydrated output in the PR
ReconcilersArgo CD, Flux (rendering off), CI apply, IaC applyApply what was hydrated

No recommendation implied. Any of these can participate; the question is only whether the output is committed and gated.

Separate wet repo, or same commit?

Separate wet repository

  • Dry repo stays small and readable
  • Wet repo can be the pull agent's source
  • Two PRs, a sync bot, and reviewers who see the effect only after the intent was merged

Same commit

  • One PR: intent and effect reviewed together
  • One history: git log answers everything
  • Larger repository; generated paths need CODEOWNERS and diff filters

If you start today, start with the same commit. Split later only if size becomes a real problem.

07

Adopting it without hurting yourself

A minimum viable path and the anti-patterns that make it fail.

~6 minutes.

A minimum viable path

  1. Pin the translators — engine versions and target API version in one tool manifest.
  2. Render in CI into a predictable path next to each unit, with stable object ordering.
  3. Commit and gate — re-render must equal committed; zero files rendered fails.
  4. Guard secrets — a rendered Secret with data fails the render.
  5. Policy on output — run your admission rules offline in the PR.
  6. Compare after apply — applied must equal rendered, minus named late values.

Steps 1–4 can be done in a week. 5 depends on how many policies you have. 6 is what makes it trustworthy.

Anti-patterns

Hand-merging generated files

On a conflict, re-render from the merged intent. A hand-merged output passes the gate only by accident.

Mocks that look real

A fake IP or ID in the committed output is indistinguishable from a real one. Use named markers.

Silent gates

Globs that match nothing, policy runs that evaluate zero rules, loops over empty lists — all exit 0.

Unpinned engines

"latest" in CI and a different version in the deploy tool means rendered ≠ applied.

Every one of these has been seen in practice. The silent gate is the most common and the most dangerous.

Making large diffs reviewable

  • Stable ordering: sort objects by kind, namespace, name — otherwise every render reshuffles.
  • Split by concern: manifests, hooks, CRD digests in separate files.
  • Ownership: CODEOWNERS on generated paths; platform reviews engine bumps.
  • Diff tooling: mark generated paths so the review UI collapses them by default, and summarise changes per object in a PR comment.
The goal is not to read every line every time. It is that every line can be read, and the unusual ones get read.

A bot comment like "3 objects changed: ClusterRole (+2 rules), Webhook (failurePolicy), Deployment (image)" gets most of the value with little reading.

When SHIM is not worth it

  • A single team, a handful of apps, no compliance requirement, charts you own and rarely bump.
  • Highly dynamic output that depends on runtime state by design.
  • Teams without the discipline to keep gates green — a red gate everyone ignores is worse than no gate.
It pays off with scale: many environments, third-party charts, auditors, and incidents where "what changed?" must be answered fast.

Be pragmatic. SHIM is a cost you pay up front to make incidents and audits cheap.

08

Takeaways

~2 minutes, then Q&A.

Five things to remember

  1. GitOps versions the intent; SHIM versions the effect as well.
  2. Push vs pull is who reconciles; hydration is what is stored. Independent choices.
  3. Gate the hydrated output: re-render = committed, policy on output, applied = reviewed.
  4. Never hydrate secrets; name late-bound values; digest the bulk.
  5. Every gate must prove it evaluated something.

If people remember only one: "review the effect, not the version number".
