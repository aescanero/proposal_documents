It was not one for Kubernetes.
This talk is about both halves.

Set the expectation: we did not adopt SHIM as a buzzword; we noticed we already were one, and found exactly where we were not.

01

The platform in one picture

Layers, archetypes, environments.

~5 minutes.

Six layers, one direction of dependency

Each layer only depends on layers below it. One known upward edge (the edge load balancer needs the gateway's NEG name) is handled by a deterministic name and a dedicated G1 rule.

Building blocks

Archetype

A versioned package of stacks that provides capabilities and requires others. Deploys a shared service with a multi-tenant contract.

Stack

A Terramate stack: one OpenTofu root module with its own state, generated from the archetype's generators.

Environment

prod, qa, dev, demos, sandbox, ephemeral-*. Each is its own VPC, cluster and edge; prod shares nothing.

Tooling: Terramate CLI for orchestration, change detection and code generation; OpenTofu for apply; outputs sharing to pass values between stacks.

Why Terramate over Terragrunt: change detection at scale, and generated code is real .tf that security scanners read without plan indirection. That last point is already a hydration argument.

The PR flow, at a glance

02

Intent: the binding

One hand-written file per environment.

~5 minutes.

An environment is its binding

# environments/qa/binding.yaml
metadata:
  name: qa
  jurisdiction: eu
  region: europe-west1
providers:
  database-platform: postgres-cloudsql
  secrets: secrets-eso-gsm
  gateway: gateway-envoy-gke
archetypes:
  - keycloak
  - sonarqube
sizes:
  runtime: medium
  • The only hand-written file for an environment (DX1).
  • Composition, providers, versions, size, region and jurisdiction vary; generators, contracts and rules do not.
  • Every name that is not a claim is derived: KSA prefixes, state keys, zones, bucket names.
  • One provider per capability per environment — resolution is a lookup, not a search.

Illustrative binding, simplified from the schema. The point: everything else about an environment is a function of this file plus the archetype manifests and the registry.

The rest of the intent

SourceHoldsWritten by
archetypes/*/manifest.yamlWhat an archetype provides, requires, its stacks and traitsArchetype owners
registry/*.yamlCapabilities, traits, zones, mandatory labels — the vocabularyPlatform team, in the spec repo
environments/*/binding.yamlWhich archetypes and providers an environment usesEnvironment owners
Generators and contractsHow a capability becomes OpenTofu; what a stack publishesPlatform team
The registry is a single source of truth. Schema enums, the policy data bundle and Gatekeeper parameters are generated from it — itself a small hydration.

The registry drift risk (R34): a label the generator stopped emitting while the admission constraint still requires it blocks deployments at admission. Generation from one source prevents it.

An environment is emitted, never copied

Copy and rename

Copy qa's stacks, replace "qa" with "sandbox". Over-matches (qa.internal), under-matches (prefixes inside values), and drifts with every later change.

Emit from intent

The resolver writes the stack tree from binding + manifests. A new environment is a new binding; the diff shows everything it creates.

No hand-kept lists either: workflow inputs, counts and forbidden public-name words are derived from environments/*/ (DX8).

This is the "promotion as a diff" property from part 1, applied to environment creation.

03

Translation: resolver and generators

From "what I want" to OpenTofu, in the pull request.

~7 minutes.

The resolver: 17 steps, fails closed

Load · Graph

  • Manifests, components, binding
  • Transitive closure, cycles
  • Capability → single provider

Validate

  • Versions, traits, runtime
  • Conflicts, stack conditions
  • Output contracts, tenant resources

Allocate · Emit

  • Address claims, idempotent by (pool, owner, purpose)
  • Firewall selectors, capacity budgets
  • Topological order → resolution.json, binding.tm.hcl
The seam between the halves is binding.tm.hcl: the resolver writes globals, the generators consume them. Neither knows the other's internals.

AM §12. Step 4 is a lookup because there is exactly one provider per capability per environment; that keeps resolution linear and its errors explainable.

What the resolver hydrates

ArtefactContentWhy it is committed
resolution.jsonThe resolved graph: providers, versions, orderReviewers see a new dependency in the diff
binding.tm.hclGlobals the generators readThe seam, versioned
Address ledgerEvery CIDR claim, by owner and purposeIdempotent allocation; a new range is visible
CMDB, declared halfStacks, edges, claimsBlast radius and destroy guards read edges, not names

All four are produced in the PR and checked like G0: re-generate and compare. The CMDB observed half is different — it is written after apply, to its own branch.

Generators: real .tf, committed

# imports/generators/v1/gen_cluster.tm.hcl (sketch)
generate_hcl "_main.tf" {
  content {
    module "cluster" {
      source        = "../../modules/gke"
      name          = global.platform.cluster_name
      region        = global.env_region
      node_pools    = global.platform.node_pools
    }
  }
}
# → stacks/platforms/gcp/qa/gke/_main.tf
  • Files prefixed _: _main.tf, _backend.tf, _sharing_generated.tf.
  • Committed to git, covered by CODEOWNERS.
  • Checkov scans them directly (G2): no plan needed.
  • One generator per capability; versioned (v1, v2) so a generator change is explicit.

Sketch, not the real generator. The point is the shape: globals in, concrete HCL out, committed.

Outputs sharing: the late-bound part

Some values only exist after a producer applies: a VPC id, a cluster endpoint, an IP.

input "network_id" {
  backend       = "default"
  from_stack_id = "gcp-qa-network"
  value         = outputs.network_id.value
  mock          = "projects/mock-project/…"
}
  • The hydrated code carries the reference, not the value.
  • Values arrive at apply time as TF_VAR_* — so never share secrets; share references.
  • Prefer globals whenever the value is known before any apply.
Mocks are allowed only in preview, are prefixed or contain mock, and are type-correct. A mock that reaches a deploy is nonsense applied.

This is the honest limit of hydration on the infrastructure side: some fields are only known at apply. The design makes them visible rather than pretending.

The top risk: an input without an after

R2 — silent and stale

Outputs sharing does not create execution order. A consumer with an input and no after generates cleanly, plans cleanly, and may apply before its producer — with yesterday's value and no error.

The rule

G1 requires the producer itself in after. A transitive path through another stack fails on purpose: it holds only until someone reorders the middle stack.

Measured: globals in stack.after are a parse error, so the resolver writes literal tag filters. The silent failure is a forgotten after, and only G1 catches it.

G0: hydrated equals source

# G0, every PR, no cloud credentials
terramate generate --detailed-exit-code   # 0 current · 2 drift · 1 error
./ci/hydrate.sh
[ -z "$(git status --porcelain -- '*/_rendered/*')" ]
  • Without G0, someone hand-edits a _main.tf, the scan passes, and the next generate silently reverts the fix.
  • --check does not exist in Terramate (it fails with "unknown flag"); measured, not assumed.
  • G0 cannot see a wrong-typed mock: it changes no generated file. G1 checks mock shapes against the contract.

05

Hydrating Kubernetes

Closing the last gap: charts rendered in the PR.

~10 minutes. The new part.

The gap: helm_release renders at apply

Platform services and middleware are Helm charts applied by OpenTofu's helm_release. In the PR the reviewer sees:

-  version = "v1.16.1"
+  version = "v1.16.2"

Not seen until apply

  • The rendered manifests
  • RBAC, webhooks, probes, defaults
  • Whether Gatekeeper will admit them
Exactly the in-flight rendering from part 1 — inside an otherwise hydrated platform.

Why helm_release and not kubernetes_manifest: the latter needs CRDs and the API server at plan time, which breaks PR previews. So charts stay; we hydrate their output.

What is written, and where (DH2)

File (next to the stack)ContentWritten by
_releases.jsonOne entry per release: name, namespace, chart, version, values fileThe generator
_values-<release>.yamlThe derived values the helm_release receives — the same onesThe generator
_rendered/<release>.yamlWhat helm get manifest will return, minus CRDs, sorted by kind/namespace/nameci/hydrate.sh
_rendered/<release>.hooks.yamlHooks: in helm template, not in helm get manifestci/hydrate.sh
_rendered/<release>.crds.sha256One line per CRD: name and digestci/hydrate.sh
Helm, gator and KUBE_VERSION are pinned in .mise.toml — the same versions on a laptop and in CI.

The values file is the key design point: the generator writes it once, and both helm_release and hydrate.sh read the same file. Two sources of values would make the render a guess.

ci/hydrate.sh, the core

mapfile -t release_files < <(git ls-files -co --exclude-standard '*/_releases.json')
[ "${#release_files[@]}" -gt 0 ] || { echo "hydrate: nothing would be rendered" >&2; exit 1; }
for rf in "${release_files[@]}"; do
  dir=$(dirname "$rf"); out="$dir/_rendered"; mkdir -p "$out"
  find "$out" -maxdepth 1 -type f -delete          # a removed release leaves nothing behind
  jq -c '.[]' "$rf" | while read -r rel; do
    # name, namespace, chart, version, values from the entry; name validated
    helm template "$name" "$chart" --version "$version" --namespace "$ns" \
      --values "$dir/$values" --include-crds --kube-version "${KUBE_VERSION:?pinned}" \
      | python3 -I ci/split-rendered.py "$out" "$name"
  done
done

split-rendered.py separates manifests, hooks and CRD digests, sorts objects, and fails on a Secret with a value or on a chart that rendered nothing.

Template in the deployment repository proposal. Tested on a fixture: deterministic across runs; a replicaCount change from 2 to 3 shows in the diff exactly as replicas: 2 → 3.

Three measured findings

Helm 3.19.0, a real certificate-management chart (v1.16.2)

--skip-crds is not enough

With CRDs enabled through values, the chart renders its 6 CRDs from templates/, and --skip-crds still emits them. Split by kind.

CRDs are ~97 %

1.25 MB of a 1.29 MB render. The reviewable rest is ~38 KB. Keep CRDs as a digest per CRD, not whole.

Hooks differ

The four post-install hook objects come out of helm template but not helm get manifest. Keep them in a separate file.

These are the kind of facts you only learn by measuring. Each one changed the design: split by kind, digest the CRDs, separate hooks so the post-apply comparison compares like with like.

Late-bound values: late:<input> (DH4)

# _values-envoy-gateway.yaml
service:
  loadBalancerIP: late:edge_ip_address
deployment:
  replicas: 3
  • A chart value that comes from an outputs-sharing input is written as a named marker.
  • The generator passes the real value as a set entry at apply.
  • G1 rejects a chart value from an input without the marker.

Never a mock here

Preview mocks are fine for a plan that is thrown away. In a committed, reviewed render, a realistic fake is indistinguishable from a real value.

The post-apply comparison masks exactly these fields and nothing else.

What is not hydrated, on purpose (DH5)

WhatWhyHow
CRDs97 % of the render; whole, the diff is unreadablename sha256 per CRD — a change is a different hash
Secret with dataA secret in git never leaves its historyThe render fails; secrets are materialised by ESO from the secret store
Charts using lookupRender differently without a clusterForbidden in our charts (G1); recorded per third-party chart, watched after apply
R73: a secret value hydrated into git is critical — every clone carries it forever. The render-time check is the guard.

The values file never receives a secret either — only references (a secret name, a key path). That rule predates hydration: outputs sharing already forbids sharing secrets.

06

Gates that prove they ran

G0–G3, admission before apply, and applied = reviewed.

~7 minutes.

Four gates

GateWhenWhatBlocking
G0 — integrityEvery PRterramate generate --detailed-exit-code; hydrate.sh and no change under _rendered/Always
G1 — structureEvery PRconftest over resolution, stacks, manifests, bindings; gator test over _rendered/Always
G2 — static scanEvery PRCheckov on the generated HCLHIGH/CRITICAL
G3 — plan scanPer environmentCheckov + conftest on plan.jsonHIGH/CRITICAL
G0, G1 and G2 need no cloud credentials. G3 runs with a read-only identity per environment, one job per environment the PR touches.

The plan identity never holds a broad viewer role: a PR from any branch can reach it, so it gets an enumerated read list.

Admission before apply (DH6)

# in ci/g1.sh, per environment
for d in $(terramate list --tags "$env"); do
  find "$d/_rendered" -name '*.yaml'
done | xargs gator test \
  --filename=policy/gatekeeper/ ...
# zero rendered files → fail

Caught in the PR

  • A pod tolerating the system pool it does not own (P11)
  • Privileges outside the gVisor sandbox pool (P13)
  • An image without a digest
  • A service account with another environment's prefix (P12)
Admission stays the last line of defence; the PR becomes the first.

Same ConstraintTemplates and Constraints the cluster runs, with the environment's parameters. This is what turns the registry-drift risk into a CI failure.

A gate that cannot run is worse than an absent one, because it reports success.

Measured examples: conftest without --all-namespaces evaluates only package main and passes with 0 tests; --data registry/ leaves the data path empty so an unknown trait passes; a nullglob loop over nothing exits 0. Every gate here counts what it evaluated and fails on zero.

Applied = reviewed (DH7)

  • After each helm_release, the deploy compares helm get manifest with _rendered/<release>.yaml, and helm get hooks with .hooks.yaml.
  • Only late:* fields are masked.
  • A difference fails the step and marks the stack drifted in the CMDB's observed half.

R72 — rendered ≠ applied

  • The provider embeds a Helm version different from the CLI
  • A third-party chart calls lookup
  • KUBE_VERSION out of step with the cluster

Without this comparison the hydrated output is a claim nobody checks. With it, review, policy and deploy all refer to the same bytes.

07

Reconciliation stays push

SHIM separates translation from reconciliation. We chose push, deliberately.

~6 minutes.

Deploy: one job per environment

Each job binds to its GitHub Environment and impersonates tf-apply-<env>@, reachable only from <env>@refs/heads/main (DX9).

Ordering: the landing zone first, non-production in parallel, prod last. Each job reads only its own state prefix. The CMDB sync writes the observed half to its own branch, never to main (that would need a protection bypass and re-trigger deploy).

Why not a pull agent (DH8)

Identity

Each environment's apply identity is bound to its Environment and to main. A pull agent is a powerful identity inside a cluster that the same infrastructure hosts.

Stateful infrastructure

Databases, keys, networks: continuous auto-apply corrects drift by destroying. Drift is detected daily and decided in a PR.

Because the model is hydrated, switching a resource class to pull later would change the reconciler, not a single committed object.

This is the delivery-independence property from part 1. Push is a choice for today, not a constraint of the model.

GitHub's on-the-fly Environments

The trap

A job that names a non-existent Environment gets one created on the fly — no reviewers, no branch policy — and its token carries environment: <env>. An identity bound to that claim alone is impersonable from any branch.

The fix

Bind apply and destroy identities to env_ref = <env>@refs/heads/main; create Environments before the binding merges; validate manual workflow inputs in a job without environment:.

R71. A detail, but it is the difference between "merge = deploy" and "any branch can deploy".

Alternatives considered on Google Cloud

ProductStanceWhy
kpt (dry/wet)idea adopted_rendered/ is the wet half, in the same commit as the intent
Config SyncnoPull, and renders inside the cluster — the in-flight rendering DH2 removes
Policy ControllernoSelf-managed Gatekeeper: one version on three clouds; gator in CI plays the same role
Config Connector / ControllernoDuplicates OpenTofu; continuous auto-correction on stateful infrastructure

The managed path on that cloud is pull with continuous reconciliation, including cloud infrastructure. The platform hydrates like kpt or Cloud Deploy, but keeps push. Equivalent reasoning applies to the other two clouds.

08

Open items and lessons

~4 minutes, then Q&A.

Still to verify

Being explicit about what is designed vs measured is part of the method. Three of these need a real cluster.

Lessons

  1. Check whether you already are a SHIM. Committed generated code plus an integrity gate is most of it.
  2. Find the one place you render in flight. For us, helm_release; for others, a GitOps controller's Helm.
  3. One values file, two readers. The thing you render and the thing you apply must read the same input.
  4. Measure the tooling. Three of our assumptions about Helm were wrong until measured.
  5. Every gate counts what it checked. Zero is a failure.
  6. Choose the reconciler per resource class. The model doesn't care.

If someone asks "what would you do differently": hydrate Kubernetes from day one, and put the post-apply comparison in before the first production deploy.
