From prompts to agent platforms

An agnostic history of how LLM applications became agent platforms — and which interfaces to build on so the next model, framework or vendor is a configuration change, not a rewrite.

Models change every few months.
Frameworks change every year.
Interfaces are what you can build a platform on.

The thesis of the talk. We will judge each era by what interface it left behind.

What we mean by "agent"

An agent is a model running in a loop: it decides the next action, calls a tool, observes the result, and repeats until a goal is met or a limit is hit.

while not done and steps < limit:
    action = model(goal, context, observations)
    result = tools[action.name](action.args)
    observations.append(result)

An agent platform adds

  • Model access and routing
  • Tools with identity and permissions
  • State, memory, durability
  • Observability and evaluation
  • Policy and guardrails

Keep the definition minimal. "Agentic" is a spectrum: from a single tool call to multi-day autonomous work.

01

Before agents

2017–2022: from a new architecture to a chat window.

~6 minutes.

The foundations

2017

The Transformer — attention-only architecture; the basis of every model since.

2018–19

Pre-trained language models (GPT-1/2, BERT) — pre-train once, adapt to many tasks.

2020

GPT-3 and few-shot prompting — the task is described in the prompt; no fine-tuning needed. "Prompt engineering" is born.

2021

Code models and browsing research — models that write code, and early work on models that search the web and cite sources.

Interface left behind: text in, text out, over an HTTP completion API.

The completion API is the first lasting interface: almost every later API is a structured variant of it.

2022: reasoning and acting, in the prompt

Instruction tuning & RLHF

Models trained to follow instructions and preferences. Makes them usable without elaborate prompts.

Chain of thought

"Think step by step": writing intermediate reasoning improves multi-step answers.

ReAct

Interleave Reason and Act: thought → tool call → observation → thought. The template of the agent loop.

Chat interfaces (Nov 2022)

A chat product brings LLMs to the general public; the message list becomes the de facto API shape.

ReAct is the conceptual ancestor of every agent loop. In 2022 it was implemented by parsing text like "Action: search[...]" out of the model's output — fragile, but it worked.

The parsing era

Thought: I need the current price.
Action: search["ACME share price"]
--- the app parses this text, runs the tool ---
Observation: 42.10 USD
Thought: Now I can answer.
Final Answer: 42.10 USD

Why it hurt

  • Regex over free text
  • Models drifted from the format
  • No types for arguments
  • Every library invented its own syntax
Lesson: when two systems talk through prose, you need a contract. The next era made it one.

Same lesson as infrastructure: an implicit interface becomes an explicit schema.

02

Tools become an API

2023: function calling, retrieval, and the first autonomous loops.

~6 minutes.

2023, quarter by quarter

Q1

Models that learn to use tools (research), chat plugins (products), and the first autonomous agent open-source projects go viral.

Q2

Function calling in model APIs: tools declared as JSON Schema, calls returned as structured JSON. "Generative agents" simulations with memory and reflection.

Q3

Open-weight models become competitive enough for real applications; multi-agent conversation frameworks appear.

Q4

Hosted assistant APIs with threads, retrieval and code execution on the provider's side.

Function calling is the key event: from now on the tool interface is a schema, not a prompt convention. Every major provider and open-weight runtime converged on JSON Schema for tool definitions.

Function calling: the first real contract

{
  "name": "get_weather",
  "description": "Current weather for a city",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" },
      "unit": { "enum": ["c", "f"] }
    },
    "required": ["city"]
  }
}
  • Tools declared with JSON Schema.
  • The model returns a structured call; the application executes it.
  • Later: structured outputs — responses guaranteed to match a schema.
  • Still per-provider: each API wraps the schema slightly differently.
Agnostic takeaway: keep tool definitions as plain JSON Schema in your code; adapt to providers at the edge.

Thin adapters per provider are cheap; tool definitions embedded in one vendor's SDK types are not.

Retrieval-augmented generation (RAG)

Grounds answers in your data without retraining. Later evolves into agentic retrieval: the model decides when and what to search, as just another tool.

Vector stores as examples: pgvector, Qdrant, Weaviate, Milvus, OpenSearch — and many search engines added vector support. Memory, in the follow-up talk, builds on the same machinery.

The first autonomous loops — and why they stalled

The promise

Give a goal; the agent plans, creates sub-tasks, calls tools and iterates until done.

What happened

  • Loops that never converged
  • Costs that grew with every step
  • Errors compounding across steps
  • No way to measure "better"
The missing pieces were not cleverness: evaluation, observability, state and limits. The rest of the history is about adding them.

With 90 % per-step reliability, ten steps succeed about a third of the time. Reliability per step, and recovery, matter more than autonomy.

03

Frameworks and orchestration

2023–2025: from chains to graphs to durable workflows.

~7 minutes. Several examples per category, no ranking.

Three generations of orchestration

Chains

Fixed sequences of prompts and tools; abstractions over prompts, retrievers and parsers.

Examples: LangChain, LlamaIndex, Haystack, Semantic Kernel

Graphs & state machines

Explicit state, nodes and edges; loops, branches, human-in-the-loop checkpoints.

Examples: LangGraph, LlamaIndex workflows, Google ADK, Pydantic AI graphs

Multi-agent

Several specialised agents conversing or handing off; a supervisor or a protocol between them.

Examples: AutoGen / Microsoft Agent Framework, CrewAI, provider agent SDKs

The trend: from "magic" abstractions to explicit control flow that engineers can test and debug.

Many teams moved from heavy frameworks to small amounts of plain code around a model client. Frameworks earn their keep with state, checkpoints and observability, not with prompt templates.

Workflows vs agents

Workflow

The code decides the path; the model fills in steps (classify, extract, summarise, route).

Predictable, cheap, testable. Use first.

Agent

The model decides the path; the code provides tools and limits.

Flexible for open-ended tasks; needs evaluation, budgets and guardrails.

Most production systems are workflows with one or two agentic steps. Start with the simplest thing that works.

Common patterns: prompt chaining, routing, parallelisation, orchestrator–workers, evaluator–optimiser. All framework-independent.

Durable execution: agents are long-running processes

  • An agent run can take minutes to days, wait for humans, and call flaky tools.
  • A crash must not mean "start again and pay again".
  • Durable execution engines persist each step and resume after failure.

Examples

Temporal, Restate, DBOS, cloud workflow services, and framework checkpointers backed by a database.

Same idea as any business workflow: idempotent steps, retries, timeouts, compensation.

Platform view: an agent is a workload with state. Treat it like one — retries, idempotency keys, budgets, and a place to inspect a stuck run.

Provider agent SDKs and hosted runtimes

From 2025, model providers and clouds ship their own agent SDKs and managed runtimes: tool calling, handoffs, tracing, sessions, hosted tools (search, code, browser).

Examples: provider agent SDKs, cloud agent builders and engines on each hyperscaler, enterprise agent platforms in SaaS suites.

Lock-in check

  • Are tools exposed via an open protocol?
  • Are traces exported in an open format?
  • Can another model run the same agent?
  • Where do state and memory live, and can you export them?

Hosted runtimes are convenient and often the right choice. The agnostic question is not "hosted or not" but "what can I take with me".

04

Protocols and standards

2024–2026: the interfaces that make the stack swappable.

~10 minutes. The most important section for an agnostic architecture.

The N × M problem

Every application integrating every tool: N × M adapters. A shared protocol: N + M. The same move as LSP for editors and language servers.

The Language Server Protocol analogy is apt and well known to engineers: before LSP every editor integrated every language; after LSP each side implements the protocol once.

Model Context Protocol (MCP)

  • Open protocol, published November 2024, connecting AI applications (clients) to tools and data (servers).
  • JSON-RPC messages; local (stdio) and remote (HTTP) transports.
  • Server primitives: tools, resources, prompts. Client features include elicitation (ask the user).
  • Authorization for remote servers based on OAuth 2.1.
  • Adopted during 2025 by the major model providers, IDEs and agent tools.

Governance

Moved to a neutral home in December 2025: the Linux Foundation's Agentic AI Foundation (AAIF), alongside other agent projects.

The importance of neutral governance: enterprises adopt standards they do not have to bet on one vendor to keep alive.

MCP in 2026: the stateless revision

  • The 2026-07-28 specification is the largest revision since launch.
  • Stateless core: no initialisation handshake or protocol sessions; each request carries what the server needs — remote servers scale behind ordinary load balancers.
  • A formal extensions model: long-running Tasks and interactive MCP Apps move out of the core.
  • Stricter OAuth requirements, trace context, a deprecation policy.

Platform impact

Breaking changes for implementers: pin protocol versions per server, test clients against both, and treat the MCP SDK like any other dependency with an upgrade plan.

Verify details against the specification itself before quoting fields; secondary write-ups differ on how disruptive the change is. The direction is clear: MCP is becoming ordinary, horizontally scalable HTTP infrastructure.

Agent-to-agent: A2A

  • MCP connects an agent to tools; A2A connects an agent to other agents that may be opaque, run elsewhere, by another team or company.
  • Announced April 2025; Agent Cards describe an agent's skills and endpoint; tasks with lifecycle and streaming updates.
  • Contributed to the Linux Foundation in June 2025; reported in August 2026 as joining the AAIF alongside MCP.

Rule of thumb

Tool if you control it and it is deterministic. Agent if it has its own reasoning, state and owner.

Other agent-communication proposals existed (e.g. ACP); they have largely converged towards A2A. Watch for consolidation rather than betting on a niche protocol.

Instructions as files: AGENTS.md and skills

AGENTS.md

A plain Markdown file in a repository telling coding agents how to build, test and follow conventions. Introduced in 2025; part of the AAIF.

Agent Skills (SKILL.md)

A folder with instructions, scripts and resources an agent loads on demand. Published as an open specification in December 2025; adopted by dozens of agent tools by mid-2026.

Agnostic win: knowledge and procedures live in version-controlled text, not inside one vendor's configuration screen.

Portability is not perfect — support levels vary between tools — but the format is plain files, so the cost of switching is low.

Observability standard: OpenTelemetry GenAI

  • Semantic conventions for model calls, token usage, tool calls and agent spans (create and invoke agent, execute tool).
  • Any OTLP-compatible backend can receive them; many agent frameworks and gateways emit them.
  • Status in October 2026: still marked Development, not Stable — attribute names can change.

Practical advice

Emit OTel now, pin the convention version you emit, and keep a mapping layer in the collector. That is the next talk.

Cross-reference: the follow-up talk "Agnostic monitoring of agents" builds entirely on this.

05

Capabilities that changed the game

2024–2026: what models and runtimes can now do.

~6 minutes.

Six capability shifts

Reasoning models

Models that spend compute thinking before answering (from late 2024; open-weight ones in early 2025). Fewer scaffolding tricks needed.

Long context

Hundreds of thousands to millions of tokens. Changes RAG trade-offs; does not remove the need for memory.

Computer & browser use

Agents operating GUIs and browsers through screenshots and actions — any app becomes a tool, slowly and fragilely.

Coding agents

Agents in terminals, IDEs and CI that read repos, run tests and open PRs — the first mass-market agent use case.

Sandboxes

Ephemeral, isolated environments to run agent-written code: micro-VMs, gVisor, containers with no credentials.

Background agents

Long-running agents triggered by events or schedules, working for hours and reporting back.

Coding agents are the reference use case because the domain has a built-in evaluator: tests and CI. Domains without one adopt agents more slowly.

Why coding agents went first

  • Verifiable outcomes: tests, type checkers, linters, CI.
  • Text-native environment: files, commands, diffs.
  • Built-in review: pull requests, code owners.
  • Built-in rollback: version control.

Pattern to copy elsewhere

Give agents an environment with a verifier, a review gate and reversibility. Where you cannot, keep a human in the loop.

This connects to infrastructure: GitOps-style review and gates make infrastructure a good domain for agents too — the agent proposes a PR, the gates and humans decide.

Open-weight and local models

Why they matter for agnosticism

  • Data residency and air-gapped deployments
  • Cost control for high-volume steps
  • A credible fallback if a provider changes terms

Serving layer

Inference servers exposing an OpenAI-compatible API have become a de facto standard: vLLM, SGLang, llama.cpp, Ollama, TGI and managed endpoints.

Agnostic takeaway: route through one model gateway; mix hosted and self-hosted models per step.

"OpenAI-compatible" here is a wire format, not a vendor choice: most providers and open runtimes accept it, which makes it the practical lowest common denominator.

06

An agnostic reference architecture

Depend on interfaces; make every layer pass the swap test.

~10 minutes. The slide people will want to photograph is next.

The layers

Top: how work arrives. Middle: the runtime and what it calls. Bottom (amber): cross-cutting concerns that every layer reports to or is constrained by. Next slides take each layer in turn.

Each layer: interface, examples, swap test

LayerDepend onExamplesSwap test
Model accessA compatible chat API behind a gatewayLiteLLM, Envoy AI Gateway, agentgateway, cloud gatewaysChange provider for one step by config
ToolsMCPYour own servers; vendor and community serversSame tool from two different agent hosts
AgentsA2AInternal and partner agentsReplace a sub-agent without touching the caller
RuntimePlain code + durable executionGraph frameworks, agent SDKs, workflow enginesPort one agent to another framework in days
InstructionsFiles in gitAGENTS.md, SKILL.mdAnother agent tool reads the same files
TelemetryOTel GenAI over OTLPAny OTLP backend, LLM-observability toolsChange backend without re-instrumenting

The swap test is the operational definition of "agnostic". Run it for real once per layer — a quarterly game day is enough.

The model gateway

  • One endpoint for every model: hosted, cloud-hosted and self-hosted.
  • Routing per step: cheap model for classification, strong model for planning.
  • Fallbacks, retries, rate limits, budgets per team or agent.
  • Central place for keys, logging, PII redaction and telemetry.

Anti-pattern

Model names and provider SDKs scattered through application code. Changing models becomes a code change in every service.

This is the cheapest agnostic win: one afternoon to put a gateway in front, and model choice becomes configuration.

The tool layer

  • Expose internal systems as MCP servers owned by the system's team.
  • Remote servers behind your normal ingress, with OAuth and per-tool scopes.
  • A registry of approved servers and versions; pin them.
  • Code execution only in sandboxes without ambient credentials.

Least privilege per tool

An agent should hold the permissions of the task, not of the person or service that started it. Prefer read-only tools; make writes explicit and reviewable.

MCP gateways (proxies in front of many MCP servers) give one place for auth, audit and allow-lists — agentgateway is one open example.

State, memory and knowledge

Run state

Where the agent is in its task. Checkpoints, durable execution.

Memory

What it learned across runs: facts, preferences, episodes.

Knowledge

Your organisation's documents and data, retrieved on demand.

Keep all three in stores you own and can export. Memory models are the subject of a dedicated follow-up talk.

Teaser for the memory talk: short-term vs long-term, semantic vs episodic vs procedural memory, write policies, forgetting, and why memory is a data-governance problem.

Evaluation is the steering wheel

  • Datasets of real tasks with expected outcomes, versioned with the code.
  • Graders: deterministic checks first, model-based judges second, humans for calibration.
  • Run in CI on every prompt, tool or model change — a model upgrade is a PR with an eval report.
  • Track cost and latency next to quality.

Examples

promptfoo, Inspect, DeepEval, Ragas, framework-native evals, LLM-observability platforms with eval features.

Without evaluation, "agnostic" is theoretical: you cannot swap a model if you cannot measure whether the new one is as good.

A worked example: the swap test in practice

  1. A support agent uses model A through the gateway, three MCP tools and a skill file.
  2. A cheaper model B is released. Add it to the gateway config; route 5 % of the classification step.
  3. CI evals run both on the task dataset: quality, cost, latency side by side.
  4. Traces in the OTel backend compare tool-call patterns and failures.
  5. Promote by config. No change to tools, skills or the runtime.
If any step requires a code change in more than one place, that is where your lock-in lives.

Walk through slowly; this is the practical summary of the architecture section.

07

Risks and governance

~5 minutes.

The risks that matter

Prompt injection

Any text an agent reads — a web page, an email, a ticket, a tool result — can carry instructions. Untrusted content plus powerful tools is the core risk.

Excessive agency

Tools with broad permissions, no confirmation on writes, credentials inherited from the user.

Data exposure

Context sent to models and tools crosses residency and contract boundaries.

Runaway cost

Loops, retries and long contexts multiply spend without anyone noticing.

Reference lists: the OWASP Top 10 for LLM applications and its agentic follow-ups. The mitigations are architectural, not prompt wording.

Controls, by layer

LayerControl
GatewayBudgets and rate limits per agent; data-classification routing (which models may see which data); redaction
ToolsScoped OAuth per tool; read-only by default; human confirmation on irreversible writes; sandboxed execution
RuntimeStep and time limits; separation of untrusted content from instructions; plan review for high-impact tasks
TelemetryEvery tool call traced with the identity it used; alerts on unusual tool patterns
ProcessAgents propose, gates and humans approve — the same PR model as infrastructure

The last row ties back to the earlier talks in this series: review and gates are how platforms already control change. Agents become one more author of changes, not an exception.

08

What comes next

~3 minutes, then Q&A.

Trends to watch

  • Protocol consolidation under neutral foundations; HTTP-native, stateless transports.
  • Agent identity: agents as first-class principals with their own credentials and audit trails.
  • Stable telemetry conventions for agents, enabling vendor-neutral monitoring.
  • Memory as infrastructure: shared, governed, exportable.
  • Agents in the change process: proposing PRs to code and infrastructure, behind the same gates as people.

The first two are on public roadmaps (the MCP roadmap lists agent identity and an HTTP-native transport among its priorities). The others are directions, not commitments.

Five things to remember

  1. Build on interfaces: compatible model API, MCP, A2A, OTel, files in git.
  2. Prefer workflows; add agency where it pays.
  3. Put a gateway in front of models and tools.
  4. No change without evals; no agent without traces.
  5. Run the swap test per layer, for real.

One-line close: "Pick models for this quarter; pick interfaces for this decade."
